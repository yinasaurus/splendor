B1) Modularization (multiple classes & methods)
    Your codebase is split across packages (see PART D). Core domain types live
    in splendor.model; rules validation in splendor.rules; orchestration in
    splendor.controller; AI in splendor.ai; I/O in splendor.ui; data loading in
    splendor.data; optional HTTP in splendor.web.

B2) Clean code & conventions
    - Meaningful names: GameController, GameRules, GameBoard, Player, Card, Noble.
    - Packages group by responsibility (not one giant default package).
    - Oracle Java conventions: classes UpperCamelCase, methods lowerCamelCase.

B3) Design principles (e.g. SRP)
    - Model (Player, GameBoard, Card) - state + simple mutations, not HTTP.
    - GameRules - validates moves (take gems, reserve, purchase, limits).
    - GameController - applies legal actions, advances turns, endgame flow.
    - ConsoleUI / WebServer - presentation & transport; call into controller.

B4) Externalized configuration (mandatory)
    File: config.properties
    - winning.points (e.g. 15 - change to 10 or 21 for shorter/longer games)
    - Per-player-count initial gem counts (comma-separated 2/3/4 players)
    - Paths to CSV: cards (same file filtered by level), nobles
    - max.gems.per.player, max.reserved.cards
    Loader: splendor.config.GameConfig reads this file.

B5) Data-driven cards & nobles
    CSV under data/ (paths declared in config.properties, not hard-coded in logic).
    CardLoader / NobleLoader parse files into model objects.

B6) Documentation
    - Javadoc-style class/method comments on public API in model/controller/rules.
    - README.md in repo explains run paths (keep for markers; course also wants slides).

PART K - POSSIBLE Q&A (QUESTIONS + SHORT ANSWERS)
================================================================================

--- OOP & DESIGN ---

Q: What is separation of concerns?
A: Model holds state. GameRules validates. GameController applies moves and turn
   flow. ConsoleUI/WebServer do I/O only and call the controller.

Q: Why not all rules inside Player?
A: Rules need bank supply and global limits; centralizing avoids duplication.

Q: What pattern for AI?
A: Strategy - AIStrategy with Easy/Medium/Hard; AIPlayer delegates.

Q: Encapsulation example?
A: Player.getGems() returns a copy so outsiders cannot corrupt internal map.

--- GameController ---

Q: What happens on take gems?
A: validateTakeGems; if ok, board.removeGems, player.addGems, stats,
   checkNobleVisits, afterSuccessfulAction.

Q: What is afterSuccessfulAction?
A: When someone first hits winning prestige, start endgame countdown for other
   players' last turns; then determineWinner / determineWinnerByPrestige.

Q: isGameOver?
A: winner != null (not simply "someone reached 15" mid-round).

Q: takeGemsWithDiscard?
A: After taking, hand may exceed max gems; discard back to bank until legal.

--- GameRules ---

Q: Take gold from bank as gem action?
A: No - validateTakeGems rejects GOLD in the take map.

Q: Take two of same color?
A: Exactly two of one non-gold color, and at least four of that color in bank
   before the take.

--- Model ---

Q: Gems vs bonuses?
A: Gems are tokens in hand. Bonuses are permanent discounts from bought cards;
   nobles check bonuses.

Q: Noble limitation in code?
A: checkNobleVisits takes first qualifying noble only; one visitedNoble flag -
   say so honestly if asked about multiple nobles.

--- Config / data ---

Q: Change win threshold?
A: winning.points in config.properties -> GameConfig -> GameRules.hasWon.

Q: Same CSV for all card levels?
A: GameController calls CardLoader.loadCards(path, level) per level; loader
   parses rows (see parseDistributionCardLine in CardLoader.java).

--- Web ---

Q: Not just static files?
A: JSON state from GameController; POST /api/action drives same engine as console.

--- Java language ---

Q: Why enum GemType?
A: Fixed set, exhaustive switch, compile-time safety.

Q: ValidationResult?
A: Static nested class in GameRules - boolean + message without exceptions for
   normal invalid moves.

Q: default on AIStrategy?
A: Java 8+ interface can share evaluateCard / canAffordCard implementations.

--- Why did my .txt show weird characters? ---
A: Usually "UTF-8 bytes interpreted as Windows-1252" or double-encoding of smart
   quotes and dashes. Fix: use UTF-8 end-to-end, or use ASCII - and ' " only in
   plain text docs.
